# VGSim Predict

`VGSim Predict` - интерфейс для подбора параметров миграции между двумя популяциями в VGsim. Приложение создаёт синтетическое наблюдение через VGsim, строит по нему траектории и признаки, а затем подбирает `mu_AB` и `mu_BA` через приближённый поиск по сетке

## Что такое VGsim

VGsim - симулятор вирусных генеалогий для эпидемических сценариев в нескольких популяциях. В этом проекте используется как генератор синтетических данных: мзадаются размеры популяций, параметры инфекции, восстановления, сэмплирования и миграции, запускается симуляцию, выгружаются события цепочки и переводятся их в таблицу наблюдаемых признаков

В интерфейсе используются две популяции: `A` и `B`. Параметр `mu_AB` отвечает за миграцию из `A` в `B`, а `mu_BA` - за миграцию из `B` в `A`.

## Основные параметры интерфейса

Параметры в приложении делятся на несколько групп: сетка поиска, параметры VGsim, параметры тестового наблюдения, параметры шума, distance, refined fit и ABC posterior.

### Сетка поиска `mu`

- `min mu` - минимальное значение миграции в сетке поиска
- `max mu` - максимальное значение миграции в сетке поиска
- `steps` - число точек сетки между `min mu` и `max mu`

Эти параметры не передаются напрямую в VGsim. Они задают область, в которой приложение перебирает кандидаты `mu_AB` и `mu_BA`

### Параметры VGsim

- `sites` - число изменяемых сайтов генома
- `pop A size` - размер популяции `A`
- `pop B size` - размер популяции `B`
- `beta` - интенсивность передачи инфекции
- `gamma` - интенсивность восстановления или удаления активного заражённого
- `sampling` - интенсивность сэмплирования
- `iterations` - максимальное число событий симуляции
- `sample size` - целевой размер выборки VGsim
- `method` - метод симуляции VGsim, обычно `direct`

### Параметры миграции VGsim

- `obs mu_AB` - истинное значение миграции из `A` в `B`, по которому создаётся тестовое наблюдение
- `obs mu_BA` - истинное значение миграции из `B` в `A`, по которому создаётся тестовое наблюдение
- `obs seed` - seed для воспроизводимости тестового наблюдения

В этом проекте миграция - это не постоянный переезд индивида из одной популяции в другую. В VGsim миграция задаёт вероятность того, что индивид из исходной популяции временно находится в другой популяции в момент возможного контакта.

То есть `mu_AB` не означает, что часть людей из `A` навсегда переехала в `B`. Это означает, что индивид из популяции `A` может оказаться в популяции `B` с вероятностью `mu_AB`

Аналогично, `mu_BA` означает вероятность того, что индивид из популяции `B` временно находится в популяции `A`

Миграция в этом проекте не является отдельной вероятностью заражения. Параметры `mu_AB` и `mu_BA` задают вероятность временного присутствия индивидов из одной популяции в другой. Они определяют, насколько часто индивиды из разных популяций могут оказаться в одной deme и, следовательно, получить возможность контакта.

Передача вируса задаётся отдельно параметром `beta`. Поэтому межпопуляционное заражение возникает не как простое произведение `beta * mu`, а через совместное действие двух механизмов: миграция создаёт возможность контакта между популяциями, а `beta` задаёт интенсивность заражения при таком контакте.

`mu_AB` - вероятность присутствия индивида из `A` в `B`
`mu_BA` - вероятность присутствия индивида из `B` в `A`

### Параметры неполной регистрации

- `шум` - включает или выключает неполную регистрацию
- `reporting rate p` - средняя доля зарегистрированных случаев
- `rate jitter` - случайное колебание reporting rate по временным точкам
- `noise seed` - seed для воспроизводимости шума

Шум применяется только к наблюдению. Кандидатные симуляции при подборе остаются чистыми, а distance считается до текущего наблюдения: чистого или зашумлённого.

### Параметры distance

- `trajectory points` - число точек временной сетки для сравнения траекторий
- `grid start (%)` - начало временной сетки в долях от времени симуляции
- `grid end (%)` - конец временной сетки в долях от времени симуляции
- `trajectory weight` - вес траекторной части distance
- `aggregate weight` - вес агрегированных summary-признаков
- `time weight` - вес различия во времени завершения симуляции
- `time extra weight` - дополнительный штраф за слишком сильное расхождение по времени
- `time tolerance frac (%)` - допустимое расхождение по времени в долях
- `migration event weight` - вес диагностических миграционных событий

В основной постановке `migration event weight` должен быть равен `0.0`, потому что реальные миграционные события обычно неизвестны

### Параметры поиска

- `top_k` - сколько лучших кандидатов брать для уточнения
- `refine_steps` - число этапов уточняющего поиска
- `refine_points` - число точек в локальной сетке вокруг лучшего кандидата
- `shrink` - коэффициент сужения области поиска
- `fit seeds` - seed, по которым усредняются кандидатные симуляции

### Параметры ABC posterior

- `samples` - число случайных кандидатов из prior
- `epsilon quantile` - доля лучших кандидатов, принимаемых в posterior
- `posterior seed` - seed для posterior-сэмплирования
- `bins` - число столбиков на гистограмме posterior

## Summary-признаки

После симуляции приложение собирает признаки:

- `final_A`, `final_B` - финальное число активных заражённых
- `peak_A`, `peak_B` - пики активных заражённых
- `time_peak_A_frac`, `time_peak_B_frac` - относительное время пиков
- `first_active_B_frac` - относительное время первого появления заражения в B
- `area_active_A`, `area_active_B` - площадь под active-траекторией
- `mean_active_A`, `mean_active_B` - среднее число активных заражённых
- `cum_infections_A`, `cum_infections_B` - накопленные заражения
- `cum_recoveries_A`, `cum_recoveries_B` - накопленные восстановления
- `t_end` - время завершения симуляции
- `mig_AB`, `mig_BA`, `mig_total`, `mig_balance_abs` - диагностические миграционные признаки
- `grid_*` - значения траекторий active/infect/recover на фиксированной временной сетке

В основной постановке `mig_AB` и `mig_BA` не участвуют в подборе, потому что в реальных данных такие параетры неизвестны. Поэтому по умолчанию `migration event weight = 0.0`. Эти колонки оставлены только для диагностики на синтетических экспериментах

## Distance

`distance` - это численная мера того, насколько кандидатная симуляция похожа на наблюдение. Чем меньше `distance`, тем лучше кандидатные параметры `mu_AB` и `mu_BA`.

Пусть:

- `s` - summary кандидатной симуляции
- `o` - summary наблюдения
- `j` - номер скалярного признака
- `t` - номер точки временной сетки
- `k` - номер траекторного ряда
- `w_j` - внутренний вес отдельного скалярного признака
- `w_k` - внутренний вес отдельного траекторного ряда
- `W_traj` - внешний вес траекторной части distance
- `W_agg` - внешний вес агрегированных summary-признаков
- `W_time` - внешний вес различия во времени завершения
- `W_extra` - внешний вес дополнительного штрафа за время
- `W_mig` - внешний вес миграционных диагностических признаков

Важно не путать два уровня весов:

```text
w_j, w_k - веса внутри одной группы признаков
W_traj, W_agg, W_time, W_extra, W_mig - веса между крупными компонентами distance
```

В интерфейсе задаются именно внешние веса:

```text
trajectory weight      -> W_traj
aggregate weight       -> W_agg
time weight            -> W_time
time extra weight      -> W_extra
migration event weight -> W_mig
```

### Нормированная ошибка одного признака

Для одного скалярного признака используется нормированная ошибка:

```text
e_j(s, o) = (s_j - o_j) / (|o_j| + 1)
```

Здесь:

- `s_j` - значение признака у кандидатной симуляции
- `o_j` - значение этого же признака у наблюдения
- `s_j - o_j` - обычная ошибка кандидата
- `|o_j| + 1` - масштаб, на который делится ошибка

Деление на `|o_j| + 1` нужно, чтобы признаки разных масштабов можно было сравнивать между собой. Например, ошибка в `10` активных заражённых и ошибка в `10` накопленных заражений могут иметь разный смысл, если сами признаки имеют разные размеры.

`+ 1` нужен, чтобы не делить на ноль, если наблюдаемое значение равно `0`.

Если `e_j` близко к нулю, кандидат хорошо совпал с наблюдением по этому признаку. Если `e_j` большое по модулю, кандидат сильно ошибся.

### Расстояние по группе скалярных признаков

Для группы скалярных признаков используется взвешенное среднеквадратичное расстояние:

```text
D_group(s, o) = sqrt(sum_j w_j * e_j(s, o)^2 / sum_j w_j)
```

Здесь:

- `D_group` - итоговое расстояние по группе признаков
- `e_j(s, o)` - нормированная ошибка по признаку `j`
- `w_j` - вес признака `j`
- `e_j(s, o)^2` - квадрат ошибки

Квадрат ошибки нужен, чтобы положительные и отрицательные ошибки не компенсировали друг друга. Если один признак завышен, а другой занижен, они не должны взаимно обнуляться.

Корень в конце возвращает значение к масштабу обычной ошибки. Поэтому эта формула похожа на RMSE, только с весами.

Если у признака большой `w_j`, он сильнее влияет на итоговое расстояние. Если маленький - слабее.

### Масштаб для траекторий

Для траекторий сначала считается масштаб по наблюдаемому ряду:

```text
scale(x) = max(percentile_90(|x|), sqrt(mean(x^2)), mean(|x|), 1)
```

Здесь:

- `x` - наблюдаемый временной ряд
- `percentile_90(|x|)` - 90-й перцентиль абсолютных значений ряда
- `sqrt(mean(x^2))` - RMS-масштаб ряда
- `mean(|x|)` - среднее абсолютное значение ряда
- `1` - минимальный безопасный масштаб

Такой масштаб нужен, чтобы сравнивать траектории не в сырых числах, а относительно типичного размера наблюдаемого ряда.

Например, если в популяции `A` активных заражённых тысячи, а в популяции `B` десятки, то сырая ошибка в `A` почти всегда будет больше. Нормировка через `scale(x)` не даёт большой популяции полностью забить маленькую.

Минимум `1` нужен, чтобы не делить на ноль и не получать слишком большой штраф на почти нулевых рядах.

### Расстояние между двумя временными рядами

После выбора масштаба расстояние между двумя рядами считается так:

```text
D_series(s, o) = sqrt(mean(((s_t - o_t) / scale(o))^2))
```

Здесь:

- `s_t` - значение кандидатной траектории в момент сетки `t`
- `o_t` - значение наблюдаемой траектории в тот же момент сетки
- `s_t - o_t` - ошибка в точке `t`
- `scale(o)` - масштаб наблюдаемого ряда
- `D_series` - расстояние между двумя временными рядами

Эта формула сравнивает форму траектории по всей временной сетке. Если кандидатная траектория близко идёт к наблюдаемой, `D_series` будет маленьким. Если графики сильно расходятся, `D_series` будет большим.

### Trajectory distance

`trajectory_distance` объединяет расстояния по шести траекторным рядам:

```text
active_A
active_B
infect_A
infect_B
recover_A
recover_B
```

Формула:

```text
D_traj = sqrt(sum_k w_k * D_series_k^2 / sum_k w_k)
```

Здесь:

- `D_traj` - итоговое расстояние по траекториям
- `D_series_k` - расстояние по одному временному ряду
- `w_k` - вес этого ряда
- `k` - номер ряда

Веса рядов:

```text
active: 2.0
infect: 1.5
recover: 1.0
```

Это означает:

- `active` важнее всего, потому что показывает текущую динамику активных заражённых
- `infect` тоже важен, потому что показывает накопленную динамику заражений
- `recover` учитывается слабее, потому что это более косвенный ряд

То есть модель сильнее штрафуется, если плохо совпадает по активным заражённым.

### Aggregate distance

`aggregate_distance` считается по агрегированным summary-признакам:

```text
D_agg = sqrt(sum_j w_j * e_j^2 / sum_j w_j)
```

В эту группу входят признаки:

```text
final_A
final_B
peak_A
peak_B
time_peak_A_frac
time_peak_B_frac
first_active_B_frac
area_active_A
area_active_B
mean_active_A
mean_active_B
cum_infections_A
cum_infections_B
cum_recoveries_A
cum_recoveries_B
```

Эти признаки описывают не всю траекторию по точкам, а её основные характеристики:

- финальные значения
- пики
- время пиков
- первое появление заражения в `B`
- площадь под active-траекторией
- среднее число активных заражённых
- накопленные заражения
- накопленные восстановления

Внутренние веса агрегированных признаков:

```text
final_A: 1.5
final_B: 1.5
peak_A: 2.5
peak_B: 2.5
time_peak_A_frac: 1.0
time_peak_B_frac: 1.0
first_active_B_frac: 2.0
area_active_A: 2.5
area_active_B: 2.5
mean_active_A: 1.5
mean_active_B: 1.5
cum_infections_A: 2.0
cum_infections_B: 2.0
cum_recoveries_A: 1.5
cum_recoveries_B: 1.5
```

Больше всего весят пики, площади под active-траекториями, накопленные заражения и первое появление заражения в `B`. Это сделано потому, что эти признаки хорошо отражают общую динамику эпидемии и межпопуляционное распространение.

`D_agg` нужен, чтобы кандидат совпадал с наблюдением не только визуально по графику, но и по важным итоговым характеристикам эпидемии.

Например, две траектории могут быть похожи по форме, но иметь разные пики или разное итоговое число заражений. `aggregate_distance` ловит такие расхождения.

### Time distance

`time_distance` сравнивает длительность кандидатной симуляции с длительностью наблюдения:

```text
D_time = |log((t_sim + 1) / (t_obs + 1))|
```

Здесь:

- `t_sim` - время завершения кандидатной симуляции
- `t_obs` - время завершения наблюдения
- `+ 1` - защита от нуля
- `log` - логарифм отношения длительностей
- `|...|` - модуль, потому что плохо и когда кандидат слишком короткий, и когда слишком длинный

Логарифм отношения удобен, потому что он штрафует относительное расхождение по времени.

Если кандидат закончился сильно быстрее наблюдения, `D_time` растёт. Если кандидат закончился сильно позже наблюдения, `D_time` тоже растёт.

Этот компонент важен, потому что правильные параметры должны давать не только похожую форму графика, но и похожую длительность эпидемического процесса.

### Time extra distance

`time_extra_distance` добавляет штраф только тогда, когда расхождение по времени превышает допустимую толерантность:

```text
D_extra = max(0, D_time - log(1 + tolerance))
```

Здесь:

- `D_time` - обычное расстояние по времени
- `tolerance` - допустимое относительное расхождение
- `log(1 + tolerance)` - граница допустимого расхождения
- `D_extra` - дополнительный штраф сверх этой границы

Если расхождение по времени маленькое, то:

```text
D_time <= log(1 + tolerance)
D_extra = 0
```

Если расхождение по времени слишком большое, то:

```text
D_time > log(1 + tolerance)
D_extra > 0
```

Например, если `time tolerance frac (%) = 0.10`, то примерно 10% расхождения по времени считаются допустимыми. Всё, что выше, получает дополнительный штраф.

`time_extra_distance` нужен, чтобы особенно сильно наказывать кандидатов, которые дают похожие траектории, но заканчиваются слишком рано или слишком поздно.

### Migration distance

`migration_distance` считается аналогично агрегированным признакам, но по диагностическим миграционным колонкам:

```text
mig_AB
mig_BA
mig_total
mig_balance_abs
first_mig_AB_frac
first_mig_BA_frac
```

Внутренние веса миграционных признаков:

```text
mig_AB: 1.0
mig_BA: 1.0
mig_total: 3.0
mig_balance_abs: 1.0
first_mig_AB_frac: 0.5
first_mig_BA_frac: 0.5
```

Эти признаки показывают внутренние миграционные события в синтетической симуляции.

Но в основной постановке `migration_distance` не должен влиять на подбор, потому что в реальных данных мы обычно не знаем настоящие скрытые миграционные события.

Поэтому базовая настройка такая:

```text
migration event weight = 0.0
```

Иначе модель будет использовать информацию, которой в реальной задаче у нас не было бы. Это было бы подглядывание в скрытые данные.

`migration_distance` можно использовать только как диагностику на синтетических экспериментах.

### Итоговая distance

Итоговая distance собирает все компоненты вместе:

```text
D_total = sqrt((
    W_traj * D_traj^2
    + W_agg * D_agg^2
    + W_time * D_time^2
    + W_extra * D_extra^2
    + W_mig * D_mig^2
) / (W_traj + W_agg + W_time + W_extra + W_mig))
```

Здесь:

- `D_total` - итоговая distance
- `D_traj` - расстояние по траекториям
- `D_agg` - расстояние по агрегированным summary-признакам
- `D_time` - расстояние по времени завершения симуляции
- `D_extra` - дополнительный штраф за слишком большое расхождение по времени
- `D_mig` - диагностическое расстояние по миграционным событиям

Внешние веса:

- `W_traj` - насколько важна форма траекторий
- `W_agg` - насколько важны агрегированные признаки
- `W_time` - насколько важно обычное расхождение по времени
- `W_extra` - насколько сильно штрафовать слишком большое расхождение по времени
- `W_mig` - насколько важны миграционные диагностические признаки

`time tolerance frac (%)` не входит в финальную формулу напрямую как вес. Он используется внутри `time_extra_distance`, чтобы определить допустимый порог расхождения по времени.

### Как читать итоговую distance

Если `distance` маленькая, кандидатная симуляция похожа на наблюдение.

Если `trajectory_distance` большая, плохо совпала форма графиков.

Если `aggregate_distance` большая, плохо совпали итоговые summary-признаки: пики, средние, площади, накопленные заражения и восстановления.

Если `time_distance` большая, симуляция заканчивается заметно раньше или позже наблюдения.

Если `time_extra_distance` большая, расхождение по времени вышло за допустимую толерантность.

Если `migration_distance` большая, внутренние миграционные события отличаются, но в основной постановке это не важно, потому что `migration event weight = 0.0`.

### Рекомендуемые веса

Для чистого наблюдения:

```text
trajectory weight = 1.0
aggregate weight = 0.75
time weight = 1.0
time extra weight = 3.0
time tolerance frac (%) = 0.10
migration event weight = 0.0
```

Для зашумлённого наблюдения:

```text
trajectory weight = 0.8
aggregate weight = 0.5
time weight = 1.0
time extra weight = 3.0
time tolerance frac (%) = 0.12
migration event weight = 0.0
```

При шуме траектории и агрегированные признаки становятся менее надёжными, поэтому их веса можно немного уменьшить. Время завершения при этом остаётся важным ориентиром.

## Equal fit

`equal-fit` ищет один общий параметр:

```text
mu_AB = mu_BA = mu
```

Алгоритм берёт одномерную сетку `mu`, запускает VGsim на каждом кандидате, усредняет summary по seed, считает distance и уточняет сетку вокруг лучших значений

## Unequal fit

`unequal-fit` ищет два разных параметра:

```text
mu_AB != mu_BA
```

Алгоритм строит двумерную сетку пар `(mu_AB, mu_BA)`, считает distance для каждой пары, выбирает лучшие пары и уточняет поиск вокруг них. Этот режим тяжелее equal-fit, потому что при `steps = 10` первый слой содержит уже `10 * 10 = 100` пар

## Fast unequal fit

`fast unequal-fit` ускоряет двумерный поиск без использования скрытых миграционных событий

Логика такая:

1. Быстрый rough-search считается только на первом seed из `fit seeds`
2. Из rough-таблицы берутся лучшие пары `(mu_AB, mu_BA)`
3. Эти пары пересчитываются на всех seed из `fit seeds`
4. Финальный ответ берётся из строк `stage_type = rerank`

По умолчанию число финальных пар для перепроверки:

```text
rerank_top = max(15, top_k * refine_points)
```

Пример выигрыша: при `steps = 7`, `top_k = 3`, `refine_steps = 2`, `refine_points = 5`, `fit seeds = 1,2,3,4,5` полный unequal требует около 995 запусков VGsim, а fast unequal - около 274 запусков

## ABC posterior

Интерфейс строит приближённую posterior-картину для equal и unequal migration

Для equal posterior сэмплируется один параметр:

```text
mu_AB = mu_BA = mu
```

Для unequal posterior сэмплируется пара:

```text
(mu_AB, mu_BA)
```

Алгоритм запускает симуляции из prior, считает distance до наблюдения и принимает только лучшие кандидаты по `epsilon quantile`

```text
accepted = distance <= epsilon
epsilon = quantile(distance, epsilon quantile)
```

На графиках используются:

- `best accepted` - лучший принятый sample по минимальной distance;
- `mean` - среднее по принятым sample;
- `median` - медиана по принятым sample;
- `95% interval` - интервал по принятым sample;
- `corr` - корреляция между `mu_AB` и `mu_BA` для unequal posterior.

`best accepted` не обязан совпадать с самым высоким столбиком гистограммы. Гистограмма показывает, где больше всего принятых sample, а `best accepted` показывает один sample с минимальной distance.

## Шум наблюдения

Интерфейс умеет включать неполную регистрацию случаев. Параметр `reporting rate p` задаёт среднюю долю зарегистрированных значений, а `rate jitter` добавляет случайное колебание этой доли по временным точкам

Базовые настройки:

```text
reporting rate p = 0.80
rate jitter = 0.03
```

Сильный шум, например `p = 0.30`, лучше использовать только как stress-test, потому что при таком недоучёте параметры миграции становятся плохо идентифицируемыми

Для noisy summary и noisy timeline используется один `noise seed`, чтобы таблица и график описывали одно и то же зашумлённое наблюдение

## Интерфейс

Основной файл приложения - `app.py`. В нём есть блоки:

- `Сетка поиска mu` - диапазон и число точек сетки
- `Параметры вируса и VGsim` - параметры симулятора
- `Параметры миграции VGsim` - истинные `obs mu_AB`, `obs mu_BA` и `obs seed`
- `Симуляция неполной регистрации` - включение или выключение underreporting
- `Параметры distance` - веса компонент distance
- `Параметры поиска` - настройки уточняющего поиска
- `Параметры ABC posterior` - настройки posterior-сэмплирования
- `Действия` - кнопки симуляции, подбора и построения графиков

Параметры `grid start (%)`, `grid end (%)` и `time tolerance frac (%)` задаются долями, а не процентами:

```text
0.00 = 0%
0.10 = 10%
1.00 = 100%
```

## Кнопки

- `Просимулировать` - создать тестовое наблюдение через VGsim
- `Подобрать equal mu` - подобрать один общий `mu`

- `ABC posterior equal` - построить posterior по equal `mu`
- `ABC posterior unequal` - построить posterior по паре `(mu_AB, mu_BA)`
